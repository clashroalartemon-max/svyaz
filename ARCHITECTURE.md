# Архитектура «Связи»

## Общая схема

```
Браузер (React 18 + Vite)
  ├─ pages/        экраны и маршруты
  ├─ components/   чат, пузыри сообщений, модалки
  ├─ ui/           маленькие компоненты (Avatar, Button, RankBadge…)
  ├─ hooks.ts      данные, сессия, тема, присутствие
  └─ lib/
       ├─ db.ts          весь доступ к Supabase
       ├─ crypto.ts      E2EE (Web Crypto + резервный TS)
       ├─ validation.ts  правила форм (чистые функции)
       ├─ format.ts      форматирование длительности и числительных
       ├─ logging.ts     маскирование ключей/паролей в логах
       ├─ ranks.ts       авто-звания по курсу и должности
       ├─ realtime.ts    broadcast-события Supabase
       ├─ sound.ts       звук уведомлений
       ├─ storage.ts     localStorage: сессия, тема, ревизия
       ├─ bus.ts         внутренняя шина событий
       └─ supabase.ts    клиент + заголовок x-user-id
```

База — Supabase (PostgreSQL + PostgREST + Realtime + Storage). Клиент не
использует Supabase Auth: вход проверяется RPC `verify_login`, а идентификатор
пользователя передаётся заголовком `x-user-id`, который читают RLS-политики
(`current_user_id()`).

> **Известное ограничение.** Заголовок `x-user-id` не подписан: с anon-ключом
> можно выдать себя за другого пользователя. Это зафиксировано в `SECURITY.md`
> (раздел 1.3) вместе с планом перехода на подписанный токен или Supabase Auth.
> Пока ограничение не закрыто, RLS защищает от случайных ошибок, но не от
> целенаправленной подделки.

Скрипты проверок (`scripts/`) запускаются на Node и загружают настоящий
`db.ts` через Vite SSR:

- `load-test.js` — 100 пользователей: регистрация, вход, чат, 5 сообщений;
- `concurrency-test.js` — параллельная отправка и защита от дублей;
- `security-rls-test.js` — демонстрация подделки `x-user-id`;
- `load-test.mjs` — HTTP-нагрузка на PostgREST.

## Поток сообщения

1. `Chat.tsx` собирает текст → `encryptFor` (личный) или `encryptForGroup`
   (групповой) шифрует содержимое случайным AES-256-GCM ключом.
2. Ключ контента заворачивается ECDH P-256 для получателя и автора.
3. `db.saveMessageOptimistic` сразу отдаёт сообщение в ленту, затем пишет
   строку в `messages`. Если сети нет — кладёт в локальную очередь и ставит
   статус «в очереди».
4. Получатель узнаёт о сообщении через Realtime-broadcast, перечитывает ленту
   (RLS отдаёт только свои чаты) и расшифровывает конверт своим приватным ключом.
5. Статусы `delivered/read` выставляет SECURITY DEFINER RPC
   (`mark_delivered`, `mark_chat_read`), чтобы RLS не разрешала править чужие
   сообщения напрямую.

## Ключи

- Пара ECDH P-256 на пользователя.
- Публичный ключ — в `profiles.public_key_jwk`.
- Приватный — в `localStorage` (`svyaz.keys.<id>`) и в базе только в виде
  `encrypted_private_key` (AES-GCM, пароль = `login:password`).
- При выходе приватный ключ, кэш и очередь удаляются с устройства.
- Колонка `encrypted_private_key` закрыта от SELECT для anon/authenticated;
  ключ отдаёт RPC `get_encrypted_key` после проверки пароля.

## RLS в двух словах

- `profiles` — публичный справочник (без приватного ключа).
- `chats`, `chat_participants`, `messages`, `media` — только участникам чата.
- Добавлять участников может владелец чата или действующий участник.
- Сообщения создаёт только автор (`sender_id = current_user_id()`), правит и
  удаляет — только автор.
- Скрытие истории (`hide_chat`, `hide_message`) и статусы — через RPC.

## Как добавить фичу

1. **Данные.** Если нужна новая таблица/колонка — добавьте идемпотентный блок
   в `supabase/schema.sql` (index/alter/create if not exists) и политики RLS.
2. **Доступ.** Функции доступа к базе — только в `src/lib/db.ts`, с типами
   из `src/types.ts`. Компоненты не обращаются к Supabase напрямую.
3. **Состояние.** Для данных используйте хуки из `src/hooks.ts`, а обновления
   после мутаций — через `emit('chat:updated')` / `emit('message:new')`.
4. **UI.** Экран — в `src/pages`, переиспользуемые части — в `src/components`
   или `src/ui`. Тяжёлые экраны подключайте через `React.lazy` в `App.tsx`.
5. **Валидация.** Правила формы — в `src/lib/validation.ts` + тест в
   `validation.test.ts`.
6. **Проверка.** `npm test`, `npm run build`, затем сценарий из `TESTING.md`.

## Соглашения

- TypeScript strict, без `any` в прикладном коде.
- Все запросы к Supabase — параметризованные (PostgREST/RPC), SQL-строки
  из пользовательских данных не собираются.
- Цвета и отступы — через CSS-переменные и Tailwind, тёмная тема обязательна.
- Новые анимации уважают `prefers-reduced-motion`.
